# 故障分析与停用说明

> 状态：**功能已停用**（2026-10-16），但**程序已改进为 v2.0**（2026-10-17）
> 原因：出现严重 bug —— **耳机已连接，音频设备仍被屏蔽**
> v2 的改动与验收见：`经验总结与改进说明.md`

---

## 一、用户看到的现象

耳机从底座拿起、正常连接（能听声音），但 Windows 声音设置里
**找不到「HECATE G3 Max」这个输出设备**，无法选择、也无法调音量。

---

## 二、实测证据链

### 证据 1：耳机确实在线

| 检测项 | 结果 |
|---|---|
| HID 接收器 (A22B) | 在场，4 个接口齐全（MI_03 Col01~04） |
| 电量 | **87%** |
| 在线标志位 | **1**（= 耳机在线） |
| 原始报文 | `d035bb0a00 01 57 ...`（下标5=01在线，下标6=0x57=87） |

### 证据 2：程序却判定设备"不存在"

`guard.log`：
```
[2026-10-16 23:51:25] 切换 -> 启用（当前 missing，电量 87）
[2026-10-16 23:51:25] 切换完成（17 ms）
```

- `当前 missing` → `device_state()` 返回 `missing`
- `切换完成（17 ms）` → **假成功**，17ms 根本来不及做任何实际操作

### 证据 3：底层硬件在场，但端点状态被卡死

注册表 `MMDevices\Audio\Render\{08e4e738-...}\DeviceState` = **4 (NOTPRESENT)**

而它指向的底层设备 `USB\VID_35BB&PID_A22B&MI_00\7&3B0EF022&0&0000`
**用 SetupAPI 查是在场的**。

→ **硬件好着，是端点状态卡死了。**

---

## 三、根因分析

### 直接原因：端点被标记为 NOTPRESENT(4)

Windows 用注册表位标志记录端点状态（注意与 `mmdeviceapi.h` 的常量不是同一套）：

| 值 | 含义 | 声音设置里 |
|---|---|---|
| `1` | ACTIVE | 可见、可用 |
| `2` | UNPLUGGED | 已拔出 |
| `4` | NOTPRESENT | **看不到** |
| `0x10000001` | DISABLED | 在"已禁用"里 |

端点处于 4 时，Windows 音频 API 不会把它列入活跃设备，声音设置里就没有它。

### 致命设计缺陷：程序无法自愈，且会误报成功

第 8 轮的修改（为了"别把已拔出的设备算作活跃"）引入了这条规则：

```python
# enum_endpoints()
present = e.get("state") != STATE_NOTPRESENT
e["live"] = (... and present)
```

接着 `set_device()` 里：

```python
live = [e for e in eps if e.get("live") and e["state"] in (STATE_ACTIVE, STATE_DISABLED)]
if not live:
    live = [e for e in eps if e.get("live")]     # ← 还是空集！
...
changed = False
for e in live:            # ← 空循环，什么都没做
    ...
if not changed:
    return True           # ★ 却返回 True（"已经是目标状态"）
```

**三个缺陷叠加**：

1. `device_state()` 只统计 `live` 端点 → 全部是 4 时返回 `missing`
2. `set_device()` 的操作集合同样排除 4 → **空集合，一个都不碰**
3. 空集合却 `return True` → **假装成功**

日志里的 `切换完成（17 ms）` 就是这么来的。

### 为什么锁死成永久状态

`apply()` 成功后会记录 `last_apply="online"`、`cur_state="enabled"`，
下一轮的短路条件命中：

```python
if self.last_apply == verdict and self.cur_state == want_state:
    return          # ← 不再重试了
```

于是程序永远停在「**自认为已启用、实际不存在**」的僵局里。

### 触发条件（无法完全确证）

端点如何从 1 变成 4，无法从日志完全还原。最可能是：
guard 以 **0.2 秒**间隔轮询，每轮都可能触发 `SetEndpointVisibility()`
切换可见性；一天下来上千次调用，与 Windows 音频设备图的重建撞在一起，
端点被留在了 NOTPRESENT。

> 复盘：当初为了"快"，把轮询压到 0.2s 并把防抖降到 1 次 —— 这直接放大了
> 可见性调用的频率。**为了速度牺牲了稳定性，是这次翻车的主因。**

---

## 四、为什么第 8 轮的验收没抓到这个 bug

第 8 轮验收时：

- 端点状态是正常的（ACTIVE / DISABLED），**没触发** `live` 过滤为空的那条路径
- 验收只测了「状态翻转 → 设备跟着变」，**没测**「端点已经处于异常状态时能否恢复」

**教训**：只验证"正常路径"是不够的，必须验证"异常状态下的自愈能力"。
自愈能力的验收方式是：**人为把状态破坏掉，再看程序能不能救回来。**

## 六、如果以后想重新启用

1. 把 `_disabled_backup/EdifierGuard.vbs` 移回启动文件夹：
   `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\`
2. **但必须先修掉下面两个问题**，否则会再次翻车。

### 必须修的问题

| # | 问题 | 修法 |
|---|---|---|
| 1 | `set_device()` 在空集合时返回 `True`（假成功） | 空集合应返回 `False` 或明确信号，让上层知道"没能操作" |
| 2 | `live` 把 NOTPRESENT 端点排除在**可操作**集合外 | "是否可用作判据"与"是否值得尝试恢复"要分开：NOTPRESENT 不能算活跃设备，但**必须仍可被启用**（`set_device` 里不能用 `live` 过滤） |
| 3 | 端点卡在 NOTPRESENT 时无自愈路径 | 启动时 / 判定期发现端点异常 且底层设备在场 → 自动写回 `DeviceState=1` |
| 4 | 轮询太快（0.2s）导致可见性调用过于频繁 | 回到 0.5~1s；且**只在判定结果真正翻转时**才调用，不做周期性重复调用 |
| 5 | 缺少"操作是否真的生效"的独立校验 | 每次切换后**用 IMMDeviceEnumerator 验证端点是否真的在活跃列表**，而不是只读注册表 |

### 建议的验收方式（关键改进）

不能只测正常路径。必须专门测：

1. 人为把端点 `DeviceState` 改成 `4` 和 `0x10000001`，看程序能否恢复
2. 人为强杀进程（任务管理器结束），重启后看能否自愈
3. 连续快速拔插耳机 20 次，看端点是否稳定
4. 跑够 24 小时，检查端点状态有没有漂移

# 八、★ 后续重大发现：真正的病根是「USB 音频接口被禁用」

> 时间：2026-10-17 00:10
> 触发：用户反馈「设备列表闪烁 + 看不到 G3 Max + **音量调不了，调完自动弹回 0**
> + HECATE 驱动软件连不上耳机」

## 8.1 结论先行

```
USB\VID_35BB&PID_A22B&MI_00\7&3B0EF022&0&0000
    问题代码 = 22 (CM_PROB_DISABLED)     ConfigFlags = 0x1
    Service  = usbaudio
    FriendlyName = HECATE G3 Max
```

**接收器的 USB 音频接口（`&MI_00`）被人为禁用了。**
这是全系统 **294 个在场设备中唯一一个异常设备**。

## 8.2 为什么会表现成"设备在、但用不了"

接收器是一个 USB 复合设备，暴露多个接口。被禁用的**只是音频接口**：

| 接口 | 状态 | 后果 |
|---|---|---|
| `USB\VID_35BB&PID_A22B`（复合设备本体） | 正常 | 设备管理器里一切"看起来"正常 |
| `...&MI_03`（HID，Col01~04） | 正常 | **电量读得到、HID 通信正常** ← 极具迷惑性 |
| **`...&MI_00`（USB Audio）** | **已禁用** | **音频链路整条不存在** |

于是出现一组自相矛盾的现象：

- 硬件在线、电量正常 → 你以为硬件没问题
- 端点注册表 `DeviceState=1`（ACTIVE）→ 声音设置里"看得见、选得中"
- 但 `IAudioEndpointVolume` **激活失败 `0x80070003`**（= ERROR_PATH_NOT_FOUND）
- → **没声音、音量调完自动弹回 0、厂商软件连不上设备**

## 8.3 关键判据（供以后快速定位）

**权威判据是 `IMMDevice::Activate(IAudioEndpointVolume)` 是否成功**，
而不是读注册表 `DeviceState`：

| 端点 | Activate 结果 |
|---|---|
| HECATE G3 Max (Render) | **失败 `0x80070003`** |
| HECATE G3 Max (Capture) | **失败 `0x80070003`** |
| 其余 9 个端点（Senary / AMD / Steam…） | 全部成功 |

**"音量调完自动弹回 0"** 是端点失去 KS 拓扑最快的识别特征。

## 8.4 排除项（已确认不是病因）

- ❌ **THX Spatial Audio APO**：其软件设备
  `SWD\DRIVERENUM\{20217009-...}#THXAPO&...` 存在且 `ConfigFlags=0x0`，完好
- ❌ **Nahimic**：同样完好
- ❌ **音频服务 / 系统层抖动**：注册表 12 秒采样 0 次变化、音频 API 15 秒采样 0 次变化
- ❌ **`devinst` 的 `{1}.` 前缀**：对比 NVIDIA / AMD / Steam 端点后确认是
  **MMDevices 的正常格式**，不是污染
- ❌ **guard / watchdog 在跑**：互斥体空闲、无自启项、无残留进程

## 8.5 修复方式（需要管理员权限）

**改注册表 `DeviceState` 治不好这个病** —— 那正是"僵尸端点"的来源。
必须真正**启用设备**：

```powershell
Enable-PnpDevice -InstanceId 'USB\VID_35BB&PID_A22B&MI_00\7&3B0EF022&0&0000' -Confirm:$false
```

交付脚本：**`FIX_AUDIO_DEVICE.bat`**（双击即可，会自动请求管理员权限，
启用设备后顺带重启 `Audiosrv` 让 AudioEndpointBuilder 重建端点）。

> 排查时的普通用户会话**没有管理员权限**
> （`IsUserAnAdmin()=False`，`Enum` 键 `PermissionError`），
> 所以这一步必须由用户在自己的 UAC 弹窗上确认。

## 8.6 关于"是谁禁用了它"

**当前 `guard.py` / `watchdog.py` 的代码里没有 PnP 禁用逻辑** ——
它只用 `IPolicyConfig::SetEndpointVisibility`（改可见性）和写注册表
`DeviceState`（改状态值），**不会**去 `DICS_DISABLE` 一个设备。

因此这个禁用**更可能来自手动操作或其它工具**（早期版本已无法考证）。
但无论来源如何，可以确定的是：

> 一旦设备被禁用，**任何**靠"改 `DeviceState` / 改可见性"来实现屏蔽的方案
> 都会失效，并且会进一步制造出"看得见却用不了"的僵尸端点。
> **这也是本项目停用的又一个理由。**

# 九、后续：v2.0 已按上述教训重写

> 时间：2026-10-17
> 结论：设备已修复（PnP 问题码 0，`Activate(IAudioEndpointVolume)` 返回 `0x00000000`），
> 程序已重写并通过 16 项自测（含真实故障注入）。

## 9.1 七条根因（详见 `经验总结与改进说明.md`）

1. 空集合返回 `True`（假成功）
2. `live` 把"能当判据"和"能对它操作"混成一个集合
3. 用缓存状态做决定，成功后不再校验（死锁）
4. "隐藏"没有定义成功标准（`DISABLED` 才是成功，`NOTPRESENT` 是失败）
5. 没有独立裁判（只看注册表，不看音频 API）
6. 失败时朝错误方向保持（应回滚为"可用"）
7. 验收只测正常路径，没测"端点已被弄坏时能否自愈"

## 9.2 对应的关键改动

| 旧 | 新 |
|---|---|
| `if not changed: return True` | `return False, "no-present-endpoint"` |
| `live` 单一集合 | `operable` / `usable` 分离 |
| 缓存短路 | 每 15 秒真读一次，偏离就重做 |
| 读注册表判断 | `IMMDeviceEnumerator` + `Activate(IAudioEndpointVolume)` |
| 隐藏成功=接口返回 0 | 隐藏成功=不在活跃列表 **且** `state==DISABLED` |
| 失败保持 | 失败回滚为可用 |
| 无熔断 | 连续 3 次失败 → `guard.fused`，只观察 |
| 看门狗只看进程 | 增加心跳，卡死 180 秒强制重启 |

## 9.3 本次验收结果

```
python guard.py --doctor     → 一切正常 ✓
python selftest.py --inject  → 16 项通过 / 0 项失败
```

其中四项关键回归：

- 人为注入 `NOTPRESENT` → 自愈成功
- 人为注入 `DISABLED` → 自愈成功
- 隐藏后状态必须是 `DISABLED`（实测两个端点均为 DISABLED，未变 NOTPRESENT）
- 让接口"谎报成功"（空操作）→ 校验能抓住，返回失败
