# 经验总结与程序改进说明

> 版本：guard v1 → **v2.0**
> 日期：2026-10-17
> 起因：一段"耳机连上了却被屏蔽、最后连声音都没了"的事故

---

## 一、一句话结论

**这次不是"某个 if 写错了"，而是整套设计缺少"我做完之后真的生效了吗"这一步。**

v1 的所有判断都依赖"我自己有没有调用成功"，而不是"系统现在到底是什么状态"。
一旦两者出现分歧（而它们确实出现了），程序就进入了**自认为成功、实际什么都没做**的死锁。
再叠加一层"底层 USB 音频接口被禁用"，最终表现成"设备看得见、选得中、没声音、音量弹回 0"。

---

## 二、事故时间线（按因果，不按时间）

| 阶段 | 发生了什么 | 后果 |
|---|---|---|
| ① 追求速度 | 为让"拿起耳机 0.3 秒出设备"，轮询压到 0.25s，下线防抖降到 2 次 | 可见性接口被高频调用，放大与音频服务重建撞车的概率 |
| ② 端点被推到 NOTPRESENT | 某次隐藏后，端点 `DeviceState` 从 `0x10000001(DISABLED)` 变成了 `4(NOTPRESENT)` | 声音设置里**看不到**这个设备了 |
| ③ `live` 过滤 | 为了"别把拔掉的设备算成活跃"，`live` 排除了 state=4 | `device_state()` 返回 `missing` |
| ④ 空集合假成功 | `set_device()` 里"可操作集合"同样排除了 4 → 空循环 → `return True` | 日志写"切换完成（17 ms）"，实际一个设备都没碰 |
| ⑤ 缓存短路死锁 | `if last_apply == verdict and cur_state == want_state: return` | 从此再也不重试，永久僵死 |
| ⑥ 另一条独立故障 | USB 音频接口 `VID_35BB&PID_A22B&MI_00` 被 PnP 禁用（问题码 22） | 端点即使 `DeviceState=1`，`IAudioEndpointVolume` 也激活失败 `0x80070003` |

第 ③④⑤ 步是**我们的锅**；第 ⑥ 步是外部原因，但 v1 **完全没有能力发现它**，
只会继续在端点层瞎折腾，把问题搅得更乱。

---

## 三、七个根因（分层看）

### A. 代码级（4 个）

1. **空集合返回成功**
   `for e in live:` 循环体一次都没执行，`changed` 仍是 `False`，却走到 `return True`。
   注释还写着"已经是目标状态"——把"没做"和"已经是"混成了同一件事。

2. **把"能当判据"和"能操作"混成一个集合**
   `live` 的语义是"这个端点可以参与在线/离线判断"，
   却被复用成"这个端点可以被开关"。于是端点一卡进 state=4，就同时失去了**被修复的资格**。
   应该是两个概念：`evidence`（能当证据）和 `operable`（能对它动手）。

3. **用缓存代替事实**
   `apply()` 成功后写 `cur_state="enabled"`，之后只比缓存。
   系统被外部改回原状、或根本没生效，程序都不会知道。

4. **"隐藏"没有定义成功标准**
   v1 认为 `SetEndpointVisibility(0)` 返回 S_OK 就算成功。
   实际上它可能把端点推到 `NOTPRESENT` —— 这不是"隐藏"，这是"消失"。

### B. 架构级（2 个）

5. **没有独立裁判**
   全程只看注册表 + 自己的返回值。注册表 `DeviceState=1` 只能说明"系统认为它该在"，
   不能说明"KS 音频链路真的通了"。唯一的权威是 `IMMDeviceEnumerator` 的活跃列表
   加上 `Activate(IAudioEndpointVolume)`。

6. **失败方向选错了**
   隐藏失败时，v1 什么也不做（保持"已隐藏"）。
   但**安全方向永远是"设备可用"**：多显示一个设备用户顶多烦一下，
   少一个设备用户就直接没声音了。

### C. 认知级（1 个）

7. **验收只测正常路径**
   第 8 轮验收时端点状态是好的，所以 `live` 为空那条分支**从来没被走到**。
   只验证"状态翻转 → 设备跟着变"，没验证"端点已经被弄坏时能不能救回来"。
   这次补上了故障注入测试，就是为了堵住这一条。

## 四、十条可复用的经验（不只适用于本项目）

1. **"没做"必须和"已经好了"区分开。** 空集合、无目标、跳过，都要有独立返回值。
2. **操作类函数不要返回 `bool`，返回 `(ok, reason)`。** 否则上层永远不知道为什么失败。
3. **每个"写操作"后面都要有一个"读回来"的独立验证。** 而且要用**另一条接口**读。
4. **验证失败时，往"用户还能用"的方向回滚。** 安全默认值不是"维持现状"，而是"恢复到可用"。
5. **缓存只用于省性能，不能用于做决定。** 决定之前必须重新读一次。
6. **定期巡检比事件驱动更可靠。** 事件丢了、被外部改了，只有巡检能发现。
7. **定义"成功的形状"，而不只是"调用成功"。** 隐藏的成功形状是 `DISABLED`；`NOTPRESENT` 是失败。
8. **分清楚问题的层级。** PnP 层 → 端点层 → 会话层。下层坏了，在上层怎么改都是徒劳，还会产生副作用。
9. **能自愈的才是好工具。** 启动时先做一次"恢复可用"，比任何防御都实在。
10. **连续失败必须熔断。** 一个会自己停下来的程序，比一个一直犯错但很勤快的程序安全得多。

## 五、v2 具体改了什么

| # | v1 的写法 | v2 的写法 | 解决 |
|---|---|---|---|
| 1 | `if not changed: return True` | `if not targets: return False, "no-present-endpoint"` | 假成功 |
| 2 | 一个 `live` 同时当判据和操作集 | `operable`（能不能动手）/ `usable`（现在能不能出声）分开 | 卡死后无法自愈 |
| 3 | `if last_apply==verdict and cur_state==want: return` | 每 15 秒真读一次 `deviations()`，偏离就重做 | 缓存死锁 |
| 4 | 只读注册表 | `IMMDeviceEnumerator` 活跃列表 + `Activate(IAudioEndpointVolume)` | 看不到僵尸端点 |
| 5 | 隐藏成功 = 接口返回 0 | 隐藏成功 = 不在活跃列表 **且** state==`DISABLED` | "隐藏"变"消失" |
| 6 | 隐藏失败保持原样 | 隐藏失败**立即回滚成可见** | 安全方向 |
| 7 | 端点层瞎折腾 | PnP 问题码非 0 时**完全不动**，只报告，进被动模式 | 治不了还添乱 |
| 8 | 0.25s 轮询 + 无脑重试 | HID 仍 0.5s，但**只在判定真正翻转时**动端点；失败指数退避 | 调用频率 |
| 9 | 无熔断 | 连续 3 次失败 → `guard.fused` → 只观察 | 防止持续伤害 |
| 10 | 无退出信号处理，强杀即卡死 | `atexit` + `SIGTERM` + 启动自愈 | 异常退出残留 |
| 11 | 看门狗只看进程是否退出 | 增加心跳（`guard.heartbeat`），卡死 180s 强制重启 | 进程活着但僵住 |
| 12 | 空 `live` 时报告 "missing" | 明确区分 `absent`（设备不在场）/`hidden`/`visible`/`mixed` | 诊断误导 |
| 13 | 无体检命令 | `--doctor` 四层检查 + 明确修复建议 | 排查靠人肉 |
| 14 | 无验收手段 | `selftest.py` 16 项，含真实故障注入 | 只测正常路径 |
| 15 | 单实例互斥体 err=5 时放行 | err=183 与 err=5 都判为"已有实例" | 高低权限双实例打架 |

### 新增的两个概念

**`operable`（能不能对它动手）**
= 底层 PnP 设备在场，无论端点 state 是 1/2/4/0x10000001。
端点卡在 4 时它仍然 `operable=True`，所以**还有救**。

**`usable`（现在能不能出声）**
= 在场 且 state==`ACTIVE`。
专门用于"用户现在能不能用"，不参与"要不要去修"的判断。

## 六、现在的判定与校验链路

```
HID 电量帧
   │  电量>0 → 在线；=0 或简帧 → 离线；读不到 → unknown（保持现状）
   ▼
[防抖] 上线立即生效 / 离线需持续 3 秒
   │
   ├── 要"隐藏"？→ 当场再读一次电量与在线位（防止刚戴上就被屏蔽）
   ▼
[PnP 预检] 目标设备问题码 != 0 ? → 不操作，只报告，被动 60 秒
   │
   ▼
[执行] IPolicyConfig::SetEndpointVisibility
   │
   ▼
[独立验证] IMMDeviceEnumerator 活跃列表 + Activate(IAudioEndpointVolume)
   │
   ├── 变可见失败 → 若 PnP 在场，写 DeviceState=1 再验一次 → 仍失败则如实报错
   └── 变隐藏失败 → **立即回滚为可见**，计一次失败
   │
   ▼
[熔断] 连续 3 次失败 → guard.fused，恢复可见，转只观察
   │
   ▼
[巡检] 每 15 秒重新核对一次，防止外部改动或静默失效
```

## 七、验收方式（这次补上的）

### 自动

```bat
python guard.py --doctor       :: 四层体检，0=健康
python selftest.py             :: 10 项纯逻辑，不改设备
python selftest.py --inject    :: 16 项，含真实故障注入，结束自动恢复
```

本次实测结果：**16/16 通过**，其中最关键的四项：

| 用例 | 结果 |
|---|---|
| 人为把端点改成 `NOTPRESENT` → 能否自愈 | ✓ 恢复为可见 |
| 人为把端点改成 `DISABLED` → 能否自愈 | ✓ 恢复为可见 |
| 隐藏后状态是否落在 `DISABLED`（而不是 `NOTPRESENT`） | ✓ 两个端点均 DISABLED |
| 接口谎报成功（空操作）能否被抓住 | ✓ 返回失败，未误报 |

### 手动（建议每月一次）

1. 运行中直接任务管理器结束 `pythonw.exe` → 重新启动后设备是否自动回到可用
2. 连续快速拔插耳机 20 次 → 端点是否稳定在 ACTIVE
3. 在设备管理器里禁用 USB 音频接口 → `--doctor` 是否报"问题码 22"且程序不瞎动
4. 连续运行 24 小时 → 检查 `guard.log` 有无反复切换、`guard.fused` 是否出现

## 八、如果你还想用这个功能

当前**仍然处于停用状态**（启动项已移除，`_disabled_backup/EdifierGuard.vbs` 是备份）。
想重新启用：

```bat
python guard.py --doctor          :: 先确认设备是健康的
python selftest.py --inject       :: 再确认程序能自愈
python install.py                 :: 装回开机自启
```

出问题时的处理顺序：

```bat
python guard.py --reset-fuse      :: 如果熔断了
python guard.py --restore         :: 如果设备被藏起来了
python guard.py --doctor          :: 还不行就体检，按提示走
```

**建议第一次先跑 `--monitor` 观察一天**（只记录判定，不动任何设备），
确认判定和你的实际使用一致，再切回 `enforce`。

## 九、还没解决的 / 仍然存在的风险

1. **PnP 层被禁用只能靠管理员修。** 程序现在的正确行为是"发现并报告、不乱动"，
   而不是"自动修"——因为修它需要 UAC，而且贸然提权做设备操作风险更大。
   已交付 `FIX_AUDIO_DEVICE.bat` 供手动执行。

2. **"是谁禁用了那个设备"仍无法定论。** v1 代码里没有 `DICS_DISABLE`，
   但历史版本已不可考。v2 明确：**任何情况下都不做 PnP 级禁用**。

3. **`SetEndpointVisibility` 本身是未公开接口**（Windows 设置内部用的），
   系统大版本更新后行为可能变化。现在有校验和熔断兜底，但仍有风险。

4. **蓝牙端点没纳入管理。** 当前只处理 USB 接收器与 USB 直连，
   蓝牙 A2DP 的历史残留端点不参与判定也不去动它 —— 这比 v1 试图"隔离"它们安全得多。

5. **`repair_device.py` 与 `guard.py` 有功能重叠。** 前者是独立诊断/修复工具，
   后者是常驻守护。两者共用同一套状态常量，如以后改常量请同步两处。
