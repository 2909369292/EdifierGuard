## 一、问题

耳机有两个状态：

| 状态 | 描述 | 音频设备是否可用 |
|---|---|---|
| **A. 只有接收器** | USB 接收器插在电脑上，耳机在底座充电/关机 | ❌ 不可用 |
| **B. 接收器 + 耳机** | 耳机开机并连上接收器 | ✅ 可用 |

Windows 的音频设备列表**永远显示**这个设备（不管耳机在不在），导致状态 A 时用户会误选一个出声不了/麦克风不通的设备。

**目标**：状态 A 时把音频设备从系统里屏蔽掉，状态 B 时恢复。全程自动、无感。

---

## 二、判定依据（核心）

**唯一的可靠信号 = 耳机电量。**

接收器是「请求-应答」型：必须主动写入查询帧，它才回复。

```
查询帧: D0 35 BB 01 + 60 字节零   →  接收器回复 op=0A 帧

回复帧结构（实测）：
  [0..2]  D0 35 BB    帧头
  [3]     0A          操作码
  [4]     00          固定
  [5]     在线标志位    1 = 耳机在线 / 0 = 在底座或关机
  [6]     电量百分比    0 ~ 100
  [11]    01   [12] 01  固定
```

**只有 `MI_03 & Col03` 这个 HID 接口支持写入**（Col01/02/04 只读，写不进去）。

### 判定规则

⚠️ **主判据是「电量 > 0」，不是「电量 == 100」。**
100% 只是测试时耳机恰好满电。电量 87、42、9 都判为在线。

| 电量读数 | 含义 | 判定 |
|---|---|---|
| **1 ~ 100**（任意非零值） | 耳机开机在线 | **online** → 启用设备 |
| **0**（明确读到） | 电量耗尽 / 在底座 | **offline** → 禁用设备 |
| **简帧**（无电量字节） | 耳机在底座或关机，接收器不上报 | **offline** → 禁用设备 |
| **读不到**（无 op=0A 帧） | 数据不足 | 沿用上次（超时 3s → unknown，保持现状） |

帧内的**在线标志位（下标 5）**是独立的第二路信号，正常情况下与电量一致；
`--status` 会一并打印，便于人工核对。

**三种"零"是分开处理的**：
1. `battery == 0` — 接收器明确应答"电量 0"
2. `battery == -1` — 收到了 op=0A 简帧，但载荷里没有电量字节（底座态的标准表现）
3. `battery is None` — 一帧都没读到（可能是偶发丢包，不能据此判定）

只有 1 和 2 会触发"禁用"；3 会沿用上次判定，避免丢包导致误切换。

### 附带保护
- **合理性校验**：电量值必须在 0~100 之间，非法值（如 255）当作"无电量"处理
- **防抖动**：连续 2 次判定一致才执行切换
- **超时保护**：数据超过 3 秒未更新 → unknown → 保持现状

> 已实测排除的方案：`PID_A22A` 设备节点（历史残留）、`op=01` FLAG、`op=07` MAC。

## 三、屏蔽手段

### 3.1 主手段：IPolicyConfig::SetEndpointVisibility ★

把音频端点设为「隐藏」，效果等同于「设置 → 声音 → 禁用设备」：

```
CLSID_PolicyConfigClient = {870AF99C-171D-4F9E-AF0D-E63DF40C2BC9}
IID_IPolicyConfig        = {F8679F50-850A-41CF-9C72-430F290290C8}
方法                     = SetEndpointVisibility(vtable[14])(devid, visible)
```

| 优点 | 说明 |
|---|---|
| **同步返回** | ~300ms 完成，不挂起 |
| **免管理员** | Windows 设置应用内部用的同一个接口 |
| **立即生效** | 不需要重启、不需要注销 |
| **应用层真实消失** | Core Audio 的 `EnumAudioEndpoints(ACTIVE)` 里查不到该设备 |

### 3.2 为什么不用 Disable-PnpDevice

`Disable-PnpDevice` 需要管理员权限，且**在耳机位于底座时会对禁用请求永久挂起**
（60 秒无返回、无异常），完全违背"快速"要求。已实测废弃。

### 3.3 屏蔽目标：两套端点都要管

G3 Max 底座版有**两套** HECATE 音频端点：

| devinst | 名字 | 何时存在 |
|---|---|---|
| `USB\VID_35BB&PID_A22B&MI_00` | `HECATE G3 Max` | **接收器**（一直插着）→ 无线使用走这套 |
| `USB\VID_35BB&PID_A22A&MI_00` | `HECATE G3 MAX GAMING HEADSET` | **耳机 USB 直连**时才有 |

两套 Render + Capture 端点**全部**纳入管理。
蓝牙 HFP 通话端点（`Hands-Free` / `BTHHFENUM`）**排除** —— 那是通话用的，不属于音乐输出。

### 3.4 孤儿端点治理

蓝牙配对会另外留下一个音频端点（instance 含 `BTHENUM\...`）。
当耳机不再通过蓝牙连接时，这个端点会变成「孤儿」——

- `DeviceState` 仍是 `1`（活动）
- 但底层设备已从系统消失
- 表现：**设备列表里有一条描述为空、音量调不了的幽灵条目**

Guard 会自动识别并隔离它们：

```
识别：devinst 含 BTHENUM 且带 0000110B(A2DP) / 0000111E(HFP)
      且用 SetupAPI（ALLCLASSES|PRESENT）查不到对应设备节点
隔离：SetEndpointVisibility(0) 隐藏 + DeviceState 钉为 UNPLUGGED(2)
```

孤儿端点**不参与** `device_state()` 判定，也不会在"解除屏蔽"时被误恢复。

## 四、可靠性设计（本轮重点修复）

### 4.1 故障安全（fail-safe）

**问题现象**：如果守护进程被意外结束（任务管理器、崩溃、系统更新），
音频端点会**永久卡在"已禁用"状态** —— 用户看到的现象就是
**"输出设备里没有 G3 Max"**。

**修复**：`guard.py` 退出时（含被强杀前的正常路径）执行 `restore_all()`，
把所有 HECATE 端点恢复成「可用」。进程结束 ≠ 设备消失。

### 4.2 看门狗（watchdog.py）

`watchdog.py` 是 guard 的监督进程：

- 启动并监护 `guard.py`
- guard 一旦退出 → **3 秒内自动重启**
- 连续快速崩溃时指数退避（3s → 4.5s → 6s → … → 30s 上限），避免疯狂重启
- 稳定运行满 60 秒后重置退避计数

启动器（VBS）现在拉的是**看门狗**，看门狗再去拉 guard —— 在离线一层的守护。

### 4.3 单实例保护

用命名互斥体 `Global\EdifierGuard_G3Max_SingleInstance` 保证同时只有一个 guard 在跑，
避免多个实例互相打架。重复启动会直接退出并记日志。

### 4.4 PID 文件

`guard.pid` / `watchdog.pid` 记录各自进程号，便于外部查活、诊断。

## 五、架构

```
┌────────────────────────────────────────────────────────┐
│            VBS 启动器（启动文件夹 / 登录自启）              │
│                        │                                │
│                        ▼                                │
│           watchdog.py（看门狗 · 崩溃自动重启）             │
│                        │                                │
│                        ▼                                │
│  ┌──────────────────────────────────────────┐          │
│  │           Edifier Guard (guard.py)        │          │
│  │                                           │          │
│  │   ┌─────────────┐      ┌──────────────┐   │          │
│  │   │ HID 轮询     │─────▶│  判定引擎     │   │          │
│  │   │ 0.2s 一次    │      │ 电量>0 ?     │   │          │
│  │   │ 单次 ~15ms   │      │              │   │          │
│  │   └─────────────┘      └──────┬───────┘   │          │
│  │          │                     │           │          │
│  │   查询帧 D0 35 BB 01     ┌─────▼──────┐   │          │
│  │   每轮都发 + 清空缓冲      │ 防抖        │   │          │
│  │          │               │ 上线1次/下线2次│  │          │
│  │          ▼               └─────┬──────┘   │          │
│  │   ┌─────────────┐             │           │          │
│  │   │ Col03 接口   │      ┌──────▼───────┐  │          │
│  │   │ 取最新 op=0A │      │ 切换端点可见性 │  │          │
│  │   └─────────────┘      │ SetVisibility │  │          │
│  │                        └──────────────┘   │          │
│  │  退出时 → restore_all()（故障安全）          │          │
│  └──────────────────────────────────────────┘          │
└────────────────────────────────────────────────────────┘
```

**特性**：
- **无感**：后台静默，无窗口无托盘
- **免配置**：登录自启，**无需管理员、不弹 UAC**
- **快速**：0.2s 轮询，单次读取 ~15ms，上线**立即**切换（拿起耳机 ≈ **0.3s** 设备出现）；
  下线防抖 2 次 ≈ **0.5s** 隐藏；单次切换 ~270ms
- **低功耗**：单线程 + sleep + 复用 HID 句柄，**实测 CPU ~7%**、内存 ~27MB
- **不卡死**：看门狗 + 故障安全 + 单实例，三重保护

### 响应延迟实测（2026-09-22，修复后）

| 指标 | 实测值 |
|---|---|
| 查询帧 → 首条回复 | **1.9 ms**（硬件本身极快） |
| 单次 `read()` 命中率 | **100%**（30/30、25/25 两轮实测） |
| 单次 `read()` 耗时 | **15 ms**（平均） |
| 完整切换（判定→生效） | **269 ms** |
| 上线响应（含防抖 1 次） | **≈ 0.3 s** |
| 下线响应（含防抖 2 次） | **≈ 0.5 s** |

> 修复前旧实现（0.6s 节流 + 读 6 帧取首帧）命中率仅 **52%**，
> 一半轮次读空 → 判定 `unknown` → 延迟累积到十多秒。
> 现已改为「每轮必写查询 + 清空陈旧缓冲 + 取最新一帧」。

## 六、文件清单

| 文件 | 作用 |
|---|---|
| `guard.py` | **核心守护程序** |
| `watchdog.py` | **看门狗**（guard 崩溃自动重启） |
| `install.py` | 安装器（写启动文件夹 + 启动看门狗） |
| `INSTALL.bat` | 一键安装（双击即可，免管理员） |
| `monitor.py` | 实时监视器（人工验收用） |
| `START_MONITOR.bat` | 双击运行监视器 |
| `lib/hid/` | 自包含依赖（含 hidapi.dll） |
| `guard.log` | 运行日志（自动轮转） |
| `watchdog.log` | 看门狗日志 |
| `guard.pid` / `watchdog.pid` | 进程号文件 |

> 注：所有交付给用户的 .bat / .py 一律使用 **ASCII 文件名**。
> 中文文件名在 cmd 里会因 GBK 解析早于 `chcp 65001` 而匹配失败。

### 用法

```bash
# 一键安装（推荐）：双击 INSTALL.bat

# 实时监视（拿起/放下耳机看切换效果）：双击 START_MONITOR.bat

# 手动检查当前判定
python guard.py --status

# 列出目标端点 + 孤儿端点
python guard.py --list

# 前台调试运行
python guard.py --debug

# 恢复端点可用（卸载前 / 救急）
python guard.py --restore
```

### 运维

```
位置: %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\EdifierGuard.vbs
停止: 结束 watchdog.exe / pythonw.exe 进程（先停看门狗，否则会被拉起）
卸载: 1) 删除上面那个 vbs 文件
      2) python guard.py --restore   （确保设备恢复可用）
```

## 七、安全设计

| 场景 | 行为 |
|---|---|
| 电量数据读不到 / 超时 3 秒 | 判定 `unknown` → **保持现状，不动作** |
| 接收器未插入 | 记录错误，保持现状，每 5 轮尝试重连 HID |
| 判定抖动 | 连续 2 次一致才切换 |
| 程序刚启动 | 6 秒宽限期，避免误判 |
| 切换失败 | 非阻塞指数退避重试（3s→6s→…→60s 上限） |
| 孤儿端点 | 自动识别隔离，不参与状态判定 |
| **guard 进程意外结束** | **退出前 `restore_all()` 恢复设备可用** |
| **guard 崩溃** | **看门狗 3 秒内拉起** |
| **重复启动** | 命名互斥体拦截，只保留一个实例 |

**原则：宁可不动，不可误禁；宁可多跑，不可失守。**
