# HECATE G3 Max（底座版）接收器 HID 协议（逆向观察记录）

> 本文记录的是**在本机观察到的**厂商 HID 报文格式，用于解释 `guard.py` 的检测逻辑。
> 它不是官方文档；**固件 / 驱动更新可能改变协议**，届时需要重新分析。

---

## 1. 设备标识

| 项目 | 值 |
|---|---|
| 接收器（dongle） | `USB\VID_35BB&PID_A22B` |
| 接收器厂商字符串 | `Jieli Technology`（杰理） |
| 产品字符串 | `HECATE G3 Max`（底座版；底座/接收器为 `PID_A22B`） |
| 耳机直连（未插入时为 `NOTPRESENT`） | `USB\VID_35BB&PID_A22A` |
| 音频端点（接收器，常驻） | `...&MI_00` 下的 Render/Capture |

Windows 只枚举到**接收器**；耳机是否开机，**不会**改变端点的 `DeviceState`
（始终 `ACTIVE`），所以必须向接收器询问。

---

## 2. HID 集合

接收器暴露 `MI_03` 下的多个集合：

| 集合 | Usage | 说明 |
|---|---|---|
| `Col01` | `0x0C`（Consumer Control） | 媒体按键，与状态无关 |
| `Col02` | `0xFF02` / Usage `2` | **只读**（本机被动监听 15s = 0 帧，接收器不主动推送） |
| `Col03` | `0xFF02` / Usage `2` | **可写 / 可读**，厂商状态通道（本机使用） |
| `Col04` | `0xFF02` / Usage `2` | **只读**（同样 0 帧） |

**结论**：接收器**不会主动上报**，只能由主机**轮询**；且要在 `Col03` 上发查询帧。

---

## 3. 查询帧

向 `Col03` 写入 64 字节：

```
D0 35 BB 01  00 00 00 00  ...  (其后补 0 至 64 字节)
```

- `D0`：报告/命令头；
- `35 BB`：厂商 VID `0x35BB`（小端）；
- `01`：查询命令。

---

## 4. 回包解析

回包同样是 64 字节，以 `D0 35 BB` 开头，`frame[3]` 为 **op（操作码）**，
`payload = frame[4:]`。

### `op = 0x0A` —— 状态帧（始终能读到）

| 字段 | 位置 | 含义 |
|---|---|---|
| 在线标志位 | `payload[1]` = `frame[5]` | `1` = 认为耳机在线 |
| 电量 | `payload[2]` = `frame[6]` | 百分比；`0` = 离线 |

**判定：**

- 电量 `> 0` → **online**；
- 电量 `== 0` → **offline**；
- **简帧**（回包里**没有**电量字节）→ **offline**；
- 完全读不到（丢包/超时）→ **unknown**（保持现状，不动作）。

### `op = 0x07` —— 对端 MAC（链路建立后才出现）

链路真正建立（耳机在网）时，会出现 `op=0x07` 帧并携带耳机侧 MAC 地址；
离线时**该帧不存在**。可作为「更接近『设备已连接』」的辅助信号。

> `guard.py --once` 会打印 `在线标志位` 与 `对端MAC(op07)`，方便现场核对。

### 离线指纹（实测）

只出现 `op=0x0A`，且 `(在线位, 电量) = (0, 0)`，**无** `op=0x07`。

---

## 5. 为什么默认**不**用「在线标志位」

「在线位」比「电量」更贴近真实链路状态，但实测存在**偶发抖动**；`guard.py`
因此默认以**电量**为主判据，另提供 `use_online_bit` 开关（默认 `false`），
并会在两者长时间不一致时打印节流告警，便于现场诊断。

## 6. 复现 / 观察工具

| 工具 | 作用 |
|---|---|
| `python guard.py --once` | 读一次并打印电量 / 在线位 / 对端 MAC |
| `python watch.py` | HID 信号观察（逆向面包板，逐步试探） |
| `gui_server.py` + `preview.html` | 本地网页「信号观察器」，展示原始帧 |
| `python monitor.py` | 终端实时监控 |
